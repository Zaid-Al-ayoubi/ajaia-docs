# Architecture & Design Decisions

## 1. Tech Stack Choices
- **Next.js (App Router):** Chosen for its full-stack capabilities, allowing us to write server-side APIs and client-side React components in the same repository. Server Components also reduce the initial JS bundle size.
- **TipTap Editor:** Instead of building a rich text editor from scratch (which is highly error-prone), TipTap was chosen for its robust headless architecture, allowing seamless integration with Tailwind CSS.
- **PostgreSQL (Supabase) + Prisma:** Prisma provides excellent TypeScript type safety. Supabase was chosen for the hosted database because it offers a generous free tier and easy connection pooling.
- **Mock Auth with HTTP-Only Cookies:** To keep the scope focused on document editing, a full auth system (like NextAuth) was skipped. Instead, a seeded user selection writes a secure `httpOnly` cookie, mimicking a real session without the overhead.

## 2. Prioritization & Tradeoffs
Given the 4-6 hour timebox, the goal was to deliver a **highly functional** core loop over a visually perfect UI. 
- **Prioritized:** Autosave (debounced), secure API routes (checking document ownership before sharing/editing), and seamless file uploads.
- **Deprioritized:** Real-time collaborative cursors (WebSockets), document version history, and true role-based permissions (Viewer vs. Editor). 
- **Known Limitation:** Using a connection pooler with Prisma in serverless environments required specific URL parameters (`pgbouncer=true`), which is handled in the environment configuration.

## 3. Data Model
- `User`: Represents the seeded users.
- `Document`: Holds the HTML content generated by TipTap, along with the owner ID.
- `Share`: A join table linking a `User` to a `Document`. It includes a `role` field to allow future expansion into view-only sharing.
